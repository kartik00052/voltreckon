# 11 - Simulator and data

- **Status:** Draft
- **Owner:** VoltReckon maintainer
- **Last verified:** 2026-11-13
- **Applies to phases:** 1-10

The simulator is a development and test tool. It generates synthetic partner data, OCPI CDRs,
faults, statements, and dispute-heavy cases so the financial path can be exercised without a
real roaming partner. It is not a production component, a load generator, a settlement
calculator, or a source of legal tax data. Its tests are consumed by
[10-testing-strategy.md](10-testing-strategy.md); the OCPI field rules are owned by
[06-ocpi-integration.md](06-ocpi-integration.md).

## 1. Current state

The module `voltreckon-simulator` exists with a package of scaffold classes:
`SimulatorApplication`, `CpoSimulator`, `OcpiPushClient`, `GenerateCommand`, `PushCommand`,
`ReplayCommand`, `DistributionModel`, `GstinFactory`, `AcnDataImporter`,
`DundeeCsvImporter`, `StationLocationImporter`, and fault classes for duplicate, late arrival,
clock skew, credit CDR, negative energy, and mid-session tariff change. The simulator POM
depends only on `voltreckon-ocpi-model`; it has no Spring Boot BOM or starters yet.

The four scenario files under `backend/voltreckon-simulator/src/main/resources/scenarios/`
(`happy-path.yml`, `duplicate-storm.yml`, `late-and-skewed.yml`, `dispute-heavy.yml`) and the
two seed files under `seed/` (`operators.yml`, `distributions.yml`) are placeholders. The Java
classes are empty scaffolds. Nothing in this file claims that generation, pushing, or replay
works today.

This file defines the target behaviour and the data rules. The first executable slice lands in
Phase 1 with `happy-path.yml`, `duplicate-storm.yml`, and the ingestion fault set.

## 2. Boundaries

**SIM-001** The simulator MUST NOT be a runtime dependency of `voltreckon-app`, and the
application MUST NOT import a simulator class. *Check:* POM graph and architecture review.

**SIM-002** The simulator MUST NOT write to a production database or call a production partner
endpoint; its default target is a local application instance. *Check:* configuration review
and target allow-list test.

**SIM-003** The simulator MUST NOT calculate an invoice, tax amount, journal, net amount, or
settlement decision independently of VoltReckon; it supplies inputs and reads outputs. *Check:*
API and class review.

**SIM-004** The simulator MUST NOT be used as evidence that a financial rule is correct; the
module tests and the real application own that evidence. *Check:* test map.

## 3. Determinism

**SIM-005** A scenario MUST be reproducible from its seed, clock start, seed files, and
scenario file; two runs with the same inputs MUST produce the same logical records and the same
manifest hash. *Check:* `SessionGeneratorDeterminismTest`.

**SIM-006** The simulator MUST use a seeded PRNG and a stable iteration order; it MUST NOT use
`Math.random`, an unseeded `SecureRandom`, a hash-map iteration order, or a locale-dependent
formatter. *Check:* code review and repeated run.

**SIM-007** The simulator MUST take time from an injected clock or a scenario clock, never from
`Instant.now`, `LocalDate.now`, or `System.currentTimeMillis`. *Check:* architecture scan.

**SIM-008** External IDs MUST be deterministic strings derived from the scenario name and a
sequence; internal entity UUIDs MUST be generated by the application, not by the simulator.
*Check:* output review.

**SIM-009** Output MUST use UTF-8, LF line endings, RFC 3339 UTC instants, ISO 4217 currency
codes, and canonical JSON with sorted keys. *Check:* manifest comparison.

**SIM-010** A run MUST write a manifest with the scenario name, seed, input hashes, record
counts, fault counts, and output hashes; a mismatch in a later run is a failure. *Check:*
manifest test.

## 4. Scenario contract

**SIM-011** A scenario MUST declare a schema version, name, seed, clock start and zone, partner
set, distributions, fault list, OCPI edition, target base URL, and output directory. Unknown
fields MUST be rejected. *Check:* scenario loader test.

**SIM-012** A scenario MUST declare its faults explicitly; hidden or probabilistic faults that
are not in the scenario are forbidden. A probability is a declared parameter, not an ambient
default. *Check:* loader and fault-count test.

**SIM-013** A scenario MUST be bounded by a record count, a byte size, or a duration; an
unbounded generator is forbidden. *Check:* loader test.

The target scenario shape is:

```yaml
schemaVersion: 1
name: happy-path
seed: 424242
clock:
  start: "2026-11-01T00:00:00Z"
  zone: Asia/Kolkata
partners:
  - ref: cpo-a
    countryCode: IN
    partyId: AAA
    roles: [CPO]
    gstinProfile: maharashtra-primary
  - ref: emsp-b
    countryCode: IN
    partyId: BBB
    roles: [EMSP]
    gstinProfile: karnataka-primary
distributions:
  sessions: 500
  energyWh: standard
  durationSeconds: standard
  startWindowDays: 30
  parkingSeconds: optional
faults:
  - type: duplicate-same
    count: 20
    probability: 0.05
target:
  baseUrl: http://localhost:8080
  ocpiEdition: "2.2.1"
output:
  directory: target/simulator/happy-path
```

This is a specification for the loader, not a claim that the current YAML files already have
these fields. The Phase 1 implementation replaces the placeholders with this shape.

## 5. Seed data

`seed/operators.yml` is the synthetic partner catalogue. It carries stable partner references,
country and party IDs, CPO/eMSP roles, GSTIN profiles with state codes, agreement terms,
currency, settlement cycle, and tariff references. `seed/distributions.yml` carries named
distributions for session count, energy, duration, start window, parking, reservation, tariff
components, currency weights, and fault weights.

**SIM-014** Seed data MUST use synthetic GSTINs and synthetic partner names; a real GSTIN, real
company, real person, real charger location, or real token MUST NOT appear. *Check:* data
review and secret scan.

**SIM-015** Every distribution MUST have a named range or parameter set in the seed file; an
unstated default is a defect because it makes runs incomparable. *Check:* seed review.

**SIM-016** A seed value MUST be stable across phases unless a migration note records the
change; changing a seed changes the expected output and requires a new expected manifest.
*Check:* manifest diff.

**SIM-017** A scenario that needs a partner not in `operators.yml` MUST declare it in the
scenario file or fail; it MUST NOT silently invent a partner. *Check:* loader test.

## 6. Fault catalogue

The simulator owns input faults, not financial outcomes. The expected result below is what the
application must do; the simulator asserts the input shape and, in integration tests, the
observed response.

| Fault | Injection | Expected application result |
|---|---|---|
| `duplicate-same` | Same external ID and payload, repeated | One accepted CDR; replay returns the stored record |
| `duplicate-conflict` | Same external ID, different total or hash | `CDR_CONFLICT` or `DUPLICATE_CDR`; original unchanged |
| `late-arrival` | Session ends days before ingest | Accepted; rating uses session start, not ingest time |
| `clock-skew` | Bounded offset between event and receive time | Accepted within tolerance; timestamps preserved |
| `credit-cdr` | New ID, `credit=true`, negated totals | Accepted; rating negates original lines and tax |
| `duplicate-credit` | Second credit for the same original | Quarantined with `DUPLICATE_CREDIT`; no financial row |
| `negative-energy` | Non-credit negative energy or cost | Quarantined with `NEGATIVE_VALUE` |
| `mid-session-tariff-change` | Publish a new version after session start | Rating uses the version effective at session start |
| `unknown-unit` | Unsupported dimension unit | Quarantined or rejected with `UNSUPPORTED_UNIT` |
| `unknown-dimension` | Unknown dimension type | Quarantined or rejected with `UNSUPPORTED_DIMENSION` |
| `missing-dimensions` | No dimensions and no usable total | Quarantined with `MISSING_DIMENSIONS` |
| `pii-present` | Driver name, phone, email, or card field | Quarantined or rejected with `PII_REJECTED` |
| `oversized-payload` | Body or raw payload above the limit | `PAYLOAD_TOO_LARGE`; no financial effect |
| `malformed-json` | Truncated or invalid OCPI body | `SCHEMA_INVALID` or `MALFORMED_JSON` |
| `partner-mismatch` | Body country/party differs from token | `PARTNER_MISMATCH`; no financial effect |
| `currency-mismatch` | Credit or tariff in another currency | Quarantine or `CURRENCY_MISMATCH` |
| `statement-duplicate` | Same statement hash imported twice | Original run returned; no second run |
| `statement-missing-line` | Statement line with no CDR | `MISSING_CDR` exception; no CDR created |

**SIM-018** A fault MUST declare its expected outcome and stable reason code; an injected fault
without an expectation is not a test. *Check:* fault catalogue review.

**SIM-019** A duplicate storm MUST generate exactly the declared number of repeats and the test
MUST assert exactly one accepted record and one financial effect. *Check:* duplicate storm IT.

**SIM-020** A credit fault MUST negate only the total fields and MUST keep the original session,
token, location, times, and currency; a mismatch is a separate fault. *Check:* credit fixture.

## 7. OCPI generation

**SIM-021** The default edition MUST be OCPI 2.2.1; OCPI 2.3.0 is selected explicitly. Every
generated payload MUST use the OCPI envelope and the fields defined by 06-ocpi-integration.
*Check:* OCPI round-trip test.

**SIM-022** A generated OCPI CDR MUST include a stable external ID, session ID, token reference,
location/EVSE/connector references, start and end instants, energy, time, currency, tariff
reference, and total cost; no driver name, phone, email, card, or bank field is generated.
*Check:* payload schema test.

**SIM-023** `OcpiPushClient` MUST send a Bearer token from the environment or a test secret
provider and MUST NOT store it in a scenario, seed file, log, or committed output. *Check:*
secret scan and header test.

**SIM-024** Replay MUST resend the recorded payload and headers from a prior run without
regenerating IDs or timestamps; it is the tool for duplicate and conflict tests. *Check:*
replay test.

## 8. Dataset importers

`AcnDataImporter` and `DundeeCsvImporter` are scaffolds for external charging datasets.
`StationLocationImporter` is a scaffold for location context. Their source datasets, versions,
licences, and checksums are not pinned in this repository.

**SIM-025** An importer MUST NOT be enabled until its dataset source, version, licence, and
SHA-256 checksum are recorded in `docs/references.md` and the dataset is approved for the
repository. *Check:* reference entry and import config.

**SIM-026** Raw third-party data MUST NOT be committed while its licence is unclear; the
repository stores the importer, a manifest, and a download or placement instruction instead.
*Check:* repository review.

**SIM-027** An importer MUST validate headers, encoding, units, currency, and duplicate keys and
MUST fail with a row report rather than guessing a missing column. *Check:* importer test.

**SIM-028** Imported location data MUST NOT be treated as a source of tariff, tax, or partner
identity; those remain VoltReckon records. *Check:* import mapping review.

Until the provenance is recorded, the simulator uses generated data only. The scaffold names
are kept so the importer decision is explicit rather than implicit.

## 9. Output and cleanup

**SIM-029** Generated data MUST be written under a build or run directory, not under `docs/` or
`src/main/resources/`; only seed and scenario definitions are committed. *Check:* `git status`
after a run.

**SIM-030** A run MUST write a manifest and a checksum for every output file so a test can
compare runs without comparing a timestamp. *Check:* manifest test.

**SIM-031** A cleanup command MUST remove only the scenario output directory; it MUST NOT delete
a database, a migration, or a committed seed file. *Check:* command review.

## 10. Phase use

| Phase | Scenario or data | Purpose |
|---|---|---|
| 1 | `happy-path`, `duplicate-storm`, credit and quarantine faults | Prove OCPI intake, dedupe, and isolation |
| 2 | `operators.yml`, tariff and agreement seed | Prove partner scope and effective tariff selection |
| 3 | `late-and-skewed`, `mid-session-tariff-change` | Prove session-start selection and deterministic rating |
| 5 | GST profiles and invoice-period sessions | Prove tax point, numbering, and credit notes |
| 6 | Statement CSV with missing, duplicate, and mismatch lines | Prove reconciliation exceptions |
| 7 | `dispute-heavy` | Prove case transitions, evidence, and invoice holds |
| 8 | Multi-invoice and credit-note periods | Prove netting, exclusions, and statement reproducibility |
| 9 | A month of accepted and quarantined events | Prove audit chain and report totals |
| 10 | OCPI 2.3.0 and invoice-reconciliation objects | Prove edition selection and V017 adapter |

**SIM-032** A scenario used by a phase MUST be committed before the phase demo and MUST be
listed in that phase's handoff with its seed and expected counts. *Check:* phase review.

## 11. Safety and security

**SIM-033** The target URL MUST pass an allow-list: loopback for local runs, an explicit test
host for CI, or an approved non-production host; a non-loopback HTTP target REQUIRES an explicit
opt-in and MUST NOT be a production hostname. *Check:* `OcpiPushClient` validation.

**SIM-034** The simulator MUST NOT print a token, Authorization header, full GSTIN, IRN, or raw
payload in logs or console output. *Check:* log capture test.

**SIM-035** A generated GSTIN MUST be syntactically valid and deliberately fictional; it MUST
NOT be a plausible real registration. *Check:* data review.

**SIM-036** The simulator MUST NOT be deployed as a production service, exposed on a public
port, or included in the application image. *Check:* packaging review.

## 12. Acceptance scenarios

```gherkin
Scenario: The same seed produces the same run
  Given the happy-path scenario with seed 424242
  When generation runs twice into different directories
  Then both manifests have the same logical hashes
  And both files contain the same external IDs and instants

Scenario: A duplicate storm has one financial effect
  Given a scenario with 20 same-payload repeats
  When the records are pushed to a local application
  Then exactly one CDR is accepted
  And the duplicates are replays, not new rows
  And no second rating result or journal exists

Scenario: Driver PII is not generated
  Given any committed scenario
  When a generated CDR is inspected
  Then it contains no driver name, phone, email, card, or bank field
  And the raw payload remains within the 64 KiB limit

Scenario: A late session uses the old tariff
  Given a session that starts before a tariff publish
  And a publish fault after the session end
  When the session is rated after the publish
  Then the session-start version is used
  And the result records a variance without mutating the tariff

Scenario: Production cannot be targeted by accident
  Given a scenario with a production base URL
  When push is attempted without an explicit non-production opt-in
  Then the client refuses the target
  And no request is sent
```

## 13. Current gaps and follow-ups

- The scenario and seed files are placeholders; the first executable scenario lands in Phase 1.
- The simulator has no Spring Boot BOM or starters; `SimulatorApplication` is a plain scaffold.
- `SessionGeneratorDeterminismTest` is empty; it becomes the first simulator test.
- Dataset provenance, licence, and checksums for the importers are not recorded; generated
  data is the only approved source until they are.
- `OcpiPushClient` currently has no transport; the implementation uses the JDK HTTP client and
  does not add a runtime dependency.
- The replay command is specified but not implemented.
